# Architecture: foundation for interactive pages

> **Internal document.** For contributors reading this repo on GitHub — not shipped in the published
> package (`deno.jsonc`'s own `publish.exclude`), not linked from the public README. It discusses
> unbuilt future components, internal audit reasoning, and gaps in a sibling package
> (`@zanix/space`) that a consumer installing `@zanix/space-ui` has no need to see in their own
> copy's docs. See [`docs/styling.md`](./styling.md)/[`docs/icons.md`](./icons.md) for the
> consumer-facing documentation that does ship.

`@zanix/space-ui` is a component library, not a framework. This document is the boundary that keeps
it that way as it grows toward supporting real interactive pages (overlays, forms, URL-synced UI,
optimistic state) — what belongs here, what belongs to [`@zanix/space`](https://jsr.io/@zanix/space)
(routing/hydration), and what always stays the consuming application's own job. It's forward-looking
by design: several of the primitives named here have zero consumers today and are not being built
yet — the point is preserving the seam they'd plug into, not building ahead of need. See
[`docs/styling.md`](./styling.md) for the separate, already-settled question of how components are
styled.

## The seven seams

These are the architectural properties every current and future stateful component must keep true.
They're not primitives (no code implements "seam 1") — they're the constraints that make the
primitives and components below composable without `space-ui` absorbing router/data/form-state
responsibility.

1. **Controlled-first, always.** Real state (`open`, `selected`, `checked`, `value`) is a plain prop
   - callback (`Modal`'s `open`/`onClose` is the reference shape), never read from
     URL/router/storage internally. This is what lets URL-sync, form submission, or optimistic UI
     drive any component from outside without `space-ui` ever needing to know they exist. A
     component may default to uncontrolled for the simple case, but the controlled escape hatch must
     exist from the day it ships, not bolted on later.
2. **State survives navigation by WHERE it lives, not by a new mechanism.** Whether an overlay
   survives a client-side navigation is a question of whether its controlling state (and, via
   `@zanix/space`'s own Comets `persist`, its DOM) lives outside the region that gets swapped —
   never something `space-ui` itself needs to solve. `ModalProvider` already works this way: it's an
   ordinary Context Provider, safe to mount once at an app-shell root a navigation never touches.
3. **Live announcements are per-component, not centralized.** Each interactive component that needs
   to tell assistive tech about a transient change (`Slider`'s "Slide N of Total") owns its own
   visually-hidden live region, in the same shape `Slider/types.ts`'s own `VISUALLY_HIDDEN_STYLE`
   already uses. No global announcer singleton — extract a shared helper only once a second real
   component needs the identical shape, the same bar that already justified extracting
   `close-on-outside.ts`.
4. **Focus management stays factored, even before it's shared.** `Modal`'s capture/trap/restore
   logic lives in one clean effect specifically so lifting it out later (once a second consumer like
   a `Drawer` is real) is a move, not a rewrite. Don't let this logic entangle with anything else
   `Modal`-specific in the meantime.
5. **Prefer native HTML mechanisms for progressive enhancement.** A disclosure/overlay should reach
   for `<details>`/`popover`/`<dialog>` where the design allows it, before a hand-rolled JS state
   machine — the concrete failure mode this avoids (a mobile nav toggle that's permanently inert
   without JS) is real and documented in the component this rescues.
6. **The first render is deterministic, always.** SSR output and the first client paint must match
   without reading `window`/`location`/`matchMedia` during render — `Counter` and `Showcase` already
   establish the pattern (start from an explicit "no real measurement yet" state, e.g. `null`,
   refine after mount). Mandatory for any future component with client-only state.
7. **`space-ui` presents data, never owns it.** No fetch, no router/history calls, no form
   submission state, no dirty-tracking. A field/overlay/list component takes already-resolved data
   as props and calls back on interaction — full stop, no exceptions carved out for convenience.

## Ownership map

| Layer                             | Owns                                                                                                                                                                                                                                                                |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`space-ui`**                    | Controlled presentational components; ARIA passthrough (`aria-current`, `aria-expanded`); focus management inside a component's own subtree; interaction mechanisms once genuine repetition exists                                                                  |
| **Application**                   | Which state is "current" (which link, which tab); reading the URL and passing the derived value down as a controlled prop; deciding where to mount a Provider component; data-fetching, optimistic policy, dirty-tracking                                           |
| **`@zanix/space`**                | Routing/navigation (Orbit); hydration timing and cross-navigation state/DOM persistence (Comets, `persist`); server-driven form progressive enhancement (`loader`/`action`/`fieldErrors`/`submitted`, 422 re-render) — deliberately with no client form-state layer |
| **Never `space-ui`, permanently** | Data-fetching of any kind; router/history manipulation; form submission/dirty-tracking state; URL parsing                                                                                                                                                           |

Making these public is a deliberate reversal of this document's own earlier default (the original
ownership classification — see the audit this document records — concluded nothing reached "public
primitive"; every one shipped internal-only, gated on this package's own real consumers). Revisited
on explicit instruction: these are small, self-contained, dependency-free building blocks (no
`@zanix/space` coupling, no app-state assumptions) that a consumer app builds the identical shape of
component around all the time — `useCloseOnOutside`/`createEscapeToCloseHandler` for a custom
dropdown, `computePosition` for a hand-rolled tooltip — so withholding them forces exactly the
duplication this package exists to avoid. The renderer-split discipline this required internally
(one file per renderer where real state/effects are involved, one shared file where the logic is
pure) is now consumer-facing too: `mod.ts` exports the React implementation of `useCloseOnOutside`/
`useFocusScope`, `mod-preact.ts` exports the independent Preact one, and both re-export the
identical module for the renderer-agnostic ones (`escape-to-close.ts`, `live-region.ts`,
`roving-focus.ts`, `positioning.ts`, `positioning-dom.ts`) — verified via the same `deno info`-based
module-graph method `dependency-boundary.test.ts` already uses for the rest of each entrypoint's own
surface.

## Deliberately rejected abstractions

- **`Presence`** (`<Presence present={cond}><Panel/></Presence>`) — no implementation, not even
  internal. `LayoutContainer`'s own `active` prop (the component this rescues, never ported as its
  own primitive) is confirmed byte-for-byte equivalent to `{condition && <Panel/>}` in every real
  consumer (a test asserts `innerHTML === ''`), and no named Presence/Show/When/Toggle abstraction
  exists anywhere in that codebase despite the plain conditional idiom recurring 3+ times unfactored
  — evidence against even a private helper.
- **A fused "dismissable layer"** (outside-click + `Escape` + focus-trap as one primitive) —
  rejected because the combinations genuinely diverge: `Toast` needs none of the three, `Combobox`
  likely wants `Escape` without a full trap, only `Modal`/`Drawer` want all three together. Kept as
  three separate, composable pieces instead (see the table above). A generic keyboard-interaction
  "key → handler" map — rejected as adding no value beyond direct `onKeyDown` composition; the one
  real transversal sub-need (roving focus) is named separately above.
- **Any form-state/submission-state machinery** — `@zanix/space` already explicitly decided against
  this ("no form store... and none is planned"); `space-ui`'s only legitimate opening is a
  presentational field component consuming `PageFieldErrors` as plain props, with zero state of its
  own.
- **URL-reading, router/history calls, or data-fetching inside any `space-ui` component** — always
  external, no exceptions, regardless of how many future components would find it convenient.

## Base components: build order and status

A dependency-ordered plan, agreed on explicitly rather than prioritized by original P0-P2 tier alone
— each entry builds on something the previous ones (or an already-shipped primitive) established.
All 14 are now shipped. `RichText` — deliberately excluded from this 14-entry plan from the start,
scoped as its own separate, last piece of work — is shipped too; see its own section below. `Select`
(row 15) is a genuinely NEW addition beyond this original plan, added once a concrete need for it
existed rather than queued from the start — the Foundation primitives table above's own
`roving-focus.ts` row already named "a future menu-button dropdown" as an anticipated consumer;
`Select` is exactly that. `Recaptcha`/`HCaptcha`/`Turnstile` (row 16) are a second such addition —
the client-side complement to `@zanix/auth`'s own `captchaGuard`, added once that server-side guard
existed and needed a real widget on the other end. `Table` (row 17) is a third such addition — the
only genuinely new component the `@zanix/console` architecture requires, added once that concrete
need existed rather than queued from the start. `Input`/`FileInput` (rows 18/19) are a fourth such
addition — `Field` (row 8) shipped with nothing real of its own to wrap; these fill that real,
confirmed gap once it existed, rather than being queued from the start alongside `Field` itself.

## RichText — a real legacy rescue, built on `formatRichText`

Unlike every entry in the table above, `RichText` has a real legacy equivalent, fully audited before
this design was built: legacy's own `RichText` was itself a thin wrapper around react-intl's ICU
rich-text tag feature — `formatMessage({id: content})` plus a `defaultRichTextElements` map of tag
name → `(chunks) => ReactNode` functions. That reframes the whole design: the right foundation isn't
a hand-rolled tag parser, it's exposing the same native capability `@formatjs/intl` (this package's
own existing, single formatting dependency at the time) already had.

- **`Formatter.formatRichText<T>`** (`src/intl/formatter.ts`) — a new, public, generic addition to
  the SAME `Formatter` interface `formatMessage` already lives on, built directly on
  `IntlShape.formatMessage`'s own generic rich-text overload (verified against its real `.d.ts`, not
  assumed: `Record<string, PrimitiveType | FormatXMLElementFn<T>>` in,
  `string | T | Array<string
  | T>` out). Required `createFormatter`'s own `createIntl(...)` call
  to widen from its default `createIntl<string>` to `createIntl<unknown>` — confirmed by a real,
  empirical type-check failure before the fix, not assumed necessary. Deferred until `RichText`
  became its first real consumer, the same "build it once a real consumer needs it" reasoning
  `usePosition` was deferred under until `Popover` arrived. `tags`/`values` merge into ONE record
  before the real call — a pure call-site convenience split, not a second semantics.
- **Population (`<props>`), redesigned without the string round-trip.** ICU tags have no attribute
  syntax, so legacy's own nested `<props>key=val</props>` tag trick (returning a stringified
  `{{($...$)}}` marker the enclosing tag's own handler had to re-find via regex and re-parse) is a
  real, necessary answer to a real constraint — kept, but the round-trip that caused two confirmed
  legacy bugs (a literal `$` breaking the regex; plain text silently misparsed as querystring for
  "component-type" tags) is gone. `<props>` now parses its content immediately and returns a typed
  sentinel value (`props-sentinel.ts`, tagged by an unexported `Symbol`, never a shape a caller's
  own chunk could accidentally satisfy), carried through the chunks array as real data. The
  enclosing tag calls `extractRichTextProps` once — merge policy kept identical to legacy's own
  `customPropsDefinition`, minus BEM: `className` concatenates, a plain `style` object shallow-
  merges, everything else is last-write-wins. `extractRichTextProps` is the one piece of this
  exported publicly — a custom tag passed through `RichText`'s own `tags` prop participates in
  population the same uniform way every built-in tag does.
- **The 34-tag legacy table, audited entry by entry, ~30 kept.** Structural/text tags (19 of them)
  kept verbatim — real existing content already authors these short names. `icon` changed target to
  `CatalogIcon` (named icons, no `href`/`viewBox` to manage). `video` — a confirmed, unconditional
  self-recursion crash bug in legacy, never once actually usable (zero real content anywhere used
  it) — now maps to the REAL `Video` component; this is the first version where it renders anything
  at all. `sus` (SuspenseFallback, never migrated, React-only) repurposed to `Skeleton` — same
  loading-placeholder intent, backed by a real both-renderer component. `page` and `lc`
  (LayoutContainer) dropped — `page` shared `video`'s own crash bug and has no real target concept
  in this package regardless (page-level composition is `@zanix/space`'s job, per the Ownership
  map); `lc` has no migrated target yet. `menu` dropped too — `Menu` has no renderer-agnostic
  `render.ts` factory the way every other target tag's component does (it needs real per-renderer
  hooks), and no consumer evidence has asked for it inside rich text specifically.
- **Markdown, explicit and expanded.** `markdown-to-jsx`'s own `/markdown` subpath — a pure
  markdown→AST parser confirmed to have ZERO React import at runtime (checked directly against its
  built JS, not its React-flavored `.d.ts` or root/`/react` entrypoint) — is walked by hand via `h`,
  the same "parameterized by h" pattern `createCatalogIcon` already established. This is exactly why
  Markdown renders through Preact with no `preact/compat` involved anywhere — a real, empirical
  dependency-boundary test
  (`mod.ts and mod-preact.ts: both reach markdown-to-jsx, but never
  through preact/compat`) proves
  it, not just asserts it. `contentFormat: 'icu' | 'markdown'` (default `'icu'`) is the one explicit
  switch — no sniffing by content or origin. `'markdown'` mode deliberately never runs `content`
  through `formatMessage`/ICU first: ICU uses `{...}` for its own syntax, and real Markdown (a
  fenced code block showing JSON, for one) commonly contains literal braces that ICU parsing would
  otherwise misinterpret before Markdown ever saw them. The legacy `_props`-on-URL convention
  (`MDLink`/`MDMedia`, routing a markdown link/image URL to `Link`/`Image`/`Video`) is kept, unified
  onto the SAME `parsePropsQuery` the ICU side's `<props>` uses instead of legacy's own second,
  parallel implementation. Covers the common node kinds a real CMS/docs document needs (paragraphs,
  headings, emphasis, links, images, code, lists, blockquotes, breaks) — tables, footnotes, GFM
  tasks, frontmatter, and raw HTML/JSX blocks are a real, disclosed v1 scope limit (render as
  nothing, never a crash), not a hidden gap.
- **`doc` is gone as a prop — moved out, not dropped.** Legacy's own `doc` mixed `fs.readFileSync`
  (Node-only, would throw in a browser/edge bundle), an unconditional client-side `fetch` with no
  caching or error handling, and a real, acknowledged-but-never-fixed hydration-mismatch bug
  (`// TODO: RECIBIR VALOR POR SSR PARA EVITAR PROBLEMAS DE HIDRATACIÓN`) directly into the
  component — a real violation of this package's own seam 7 ("presents data, never owns it"),
  applied here explicitly for the first time rather than assumed exempt. `resolveRichTextDocument`
  (`RichText/resolve.ts`) is the clean replacement: a standalone, `fetch`-based async resolver
  (never `readFileSync`), mirroring `StructuredData/resolve.ts`'s own "component plus an adjacent
  pure/async resolver" precedent exactly — not a new abstraction invented to preserve the
  capability, an existing one reused. Called from a `@zanix/space` `loader`, `content` arrives at
  `RichText` already resolved — deterministic first render by construction, never legacy's own
  client-only fetch state. A failed load rejects with a real error instead of legacy's own silent
  fetched-error-page-as-content bug.
- **`RichText` requires `<IntlProvider>` uniformly**, even in `'markdown'` mode (which doesn't
  actually use the formatter) — a deliberate simplification: one invariant to document instead of a
  conditional one, and React's own Hooks rules make `useIntl()` awkward to call conditionally
  regardless.

See `RichText`'s own `index.ts`/`index.preact.ts`, `tags.ts`, `markdown.ts`, `props-sentinel.ts`,
`parse-props-query.ts`, and `resolve.ts` doc comments for the full, load-bearing detail behind each
decision above — this section is the summary, not the source of truth.

## Known gaps in `@zanix/space` itself (not `space-ui`'s to fix)

No client hook for URL-derived state (a `useSearchParams` equivalent), no `isPending`/`isNavigating`
exposed at the framework level, and no focus management after an Orbit swap (previously free from a
full page reload, now a real gap since Orbit does soft navigation). `PageFieldErrors`
(`src/typings/page.ts`) is defined and attached to `PageContext`, but not re-exported from
`@zanix/space`'s own `mod.ts` (confirmed by direct audit — every barrel and subpath export checked)
— no consumer can `import type { PageFieldErrors } from '@zanix/space'` today, only reach it
structurally through the exported `PageContext`. `Field`'s own design deliberately doesn't depend on
this being fixed (see its own row above). Reported here for visibility; resolving them is out of
this package's scope.
